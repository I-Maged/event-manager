## Ordered task list

### Task 1 — Production seam: extract check-in cores
Files: `src/lib/check-in.ts` (new), `src/app/events/actions.ts` (edit)

1. Create `src/lib/check-in.ts` exporting:
   - `checkInAttendeeCore(eventId, attendeeUserId, organizerId): Promise<{ok:true; checkedInAt: string|null} | {ok:false; error: string}>` — single conditional `updateMany` where `checkedInAt IS NULL AND status='GOING'`; if 0 rows, read row: missing → "Attendee not found.", not GOING → "Only Going attendees can be checked in.", else idempotent success with stored `checkedInAt`. Wrap in try/catch → `{ok:false, error:'Check-in failed. Please retry.'}`.
   - `undoCheckInCore(eventId, attendeeUserId, organizerId): Promise<{ok:true; checkedInAt: string|null} | {ok:false; error: string}>` — `updateMany` where `checkedInAt IS NOT NULL` → set both null; read row; missing → "Attendee not found."; else `{ok:true, checkedInAt: null}`.
   - Both return the stored timestamp as ISO string (matches action's JSON shape).
2. Refactor `checkInAttendee` / `undoCheckIn` in `src/app/events/actions.ts` to call the cores (keep `requireOrganizer`, `enforceRateLimit('checkIn')`, `revalidateEvent` in the action).
3. `npm run typecheck` + `npm run lint src/lib/check-in.ts src/app/events/actions.ts`.

Covers Phase 3.6 prerequisite.

### Task 2 — `tests/db/rsvp.test.ts` — RSVP core, capacity, cancellation (3.1, 3.2, 3.3)
`beforeEach: resetDomainTables()`. Use `makeEvent`, `makeRsvp`, `upsertRsvpCore`, `cancelRsvpCore`, `promoteFromWishlist`.

**3.1 RSVP core & capacity (12):**
- Uncapped event accepts GOING / MAYBE / NOT_GOING.
- Re-saving the same status is idempotent (same row id, status unchanged).
- Changing status updates the same row (upsert, not insert).
- `attendeeName` stamped on create and on update.
- Capped event with a free seat accepts GOING.
- Capped event with no free seat returns WAITLISTED.
- Existing GOING user re-clicking GOING does not become waitlisted.
- Switching GOING→MAYBE frees a seat (promotion may occur).
- Switching GOING→NOT_GOING frees a seat.
- Switching away from GOING promotes the oldest waitlisted user.
- Waitlist position is 1-based, ordered by `createdAt`.
- Equal `createdAt` rows have a deterministic order (tie-break on `id`); assert position is stable/repeatable.
- Unknown event → `{ok:false, error:'Event not found.'}`.
- Ended event → `{ok:false, error:'This event has ended.'}` and no RSVP row written.

**3.2 Wishlist promotion (9):**
- Promotion is oldest-first.
- Promoted rows get `promotedAt` set.
- Promoted user ids are returned to the caller.
- No promotion while `room <= 0`.
- Promotion drains a queue larger than one batch (seed > batch waitlisted, confirm all promoted across loops).
- A user who joins a full event is promoted in the same call when a seat frees (switch another GOING→NOT_GOING in the same locked flow).
- Promotion preserves `attendeeName` and other row fields.
- Promotion never exceeds the cap (final GOING count ≤ cap).

**3.3 Cancellation (7):**
- Cancel removes the caller's row.
- Cancel promotes waitlisted users when a seat frees.
- Cancel reports `hadRsvp` correctly (true when row existed, false when not).
- Cancel returns organizer id and `organizerNotify` preference.
- Cancel with no row is safe (`ok:true`, `hadRsvp:false`).
- Cancel on an ended event is rejected without writes.
- Cancel on an unknown event is rejected.

### Task 3 — `tests/db/check-in.test.ts` — check-in (3.6)
Uses new `checkInAttendeeCore` / `undoCheckInCore` from `src/lib/check-in.ts`. Seed a GOING RSVP row per test.

- First check-in stores `checkedInAt` and `checkedInBy`.
- Second check-in is idempotent, returns the same timestamp.
- Checking in MAYBE / NOT_GOING / WAITLISTED row is rejected.
- Checking in a missing attendee is rejected.
- Undo clears both `checkedInAt` and `checkedInBy`.
- Undo twice is safe, both fields null.
- Two concurrent check-ins store exactly one timestamp (`Promise.all`).
- Two concurrent undos leave both fields null.

### Task 4 — `tests/db/invite.test.ts` — invite links (3.5)

- Two concurrent creates return the same token (`Promise.all`).
- Public events reject invite creation.
- Regenerate replaces the token.

- Revoke clears the token.

- Unknown event is handled (`Event not found.`).
- Accept creates GOING when space is available.
- Accept creates WAITLISTED when full.
- Accept on an ended event is rejected.
- Accept by the host is rejected.
- Accept with an unknown token is rejected.

### Task 5 — `tests/db/rsvp-concurrency.test.ts` — add 3 scenarios (3.4)
Append to the existing file (keep `ROUNDS`/`RACERS` env-tunable).

- Capacity raise during concurrent writers cannot overbook (cap 1, N racers GOING, then raise cap inside a locked transaction; final GOING ≤ new cap, no double-GOING).

- Mutations for different events do not block each other (run RSVP writes on event A and event B concurrently; both complete; assert isolation — no cross-event serialization failure).

## Risks & notes

- `upsertRsvpCore`/`cancelRsvpCore` use `new Date()` for the "ended" check; use `pastDate()` / `futureDate()` factories and avoid wall-clock dependence.
- Advisory locks are transaction-scoped (`pg_advisory_xact_lock`), correct through PgBouncer transaction mode (the pooled URL). The `db` project is serial so test files never interleave.
- `promoteFromWishlist(tx, eventId, cap)` requires `lockEvent` already held — call it inside a `$transaction` that first locks.
- `updateEventCore` extraction must preserve the timezone-preservation rule (same wall clock → keep legacy `timeZone` null) so tests asserting timezone behavior stay green.
- `makeRsvp` defaults status to `GOING`; override explicitly for WAITLISTED/MAYBE/NOT_GOING rows.
- `resetDomainTables()` truncates `Event`, `RSVP`, `Comment`, `Notification`, `RateLimit`; never `neon_auth`.
